# Data Quality & Validation Rules

## 1. Purpose

The validation layer is responsible for identifying records that do not satisfy the structural, business, or referential requirements of the source data.

Invalid records must be explicitly identified and routed to the rejection process rather than silently removed.

---

# 2. Validation Categories

The validation framework contains four primary categories:

1. Completeness
2. Validity
3. Uniqueness
4. Referential Integrity

# 5. Validation Outcome

Each transaction should receive a validation outcome.

Possible outcomes:

- VALID
- REJECTED

Rejected records must also contain a reason describing the validation failure.

Example:

```text
transaction_id: TXN00012345
validation_status: REJECTED
validation_reason: INVALID_AMOUNT

---

# 6. Validation Output Model

The validation process produces two logical outputs.

## 6.1 Validation Result

The validation result contains one record for each processed source record.

| Column | Description |
|---|---|
| record_key | Identifier of the source record |
| validation_status | VALID or REJECTED |

Example:

```text
record_key     validation_status
TXN000001      VALID
TXN000002      REJECTED
TXN000003      VALID

## Response Codes

Supported response codes:

- 00 - Successful transaction
- 05 - Do not honor / general decline
- 09 - Transaction pending
- 14 - Invalid transaction
- 51 - Insufficient funds
- 91 - Issuer or gateway unavailable
